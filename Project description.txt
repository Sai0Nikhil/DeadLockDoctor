Must build (core spec)
A resource manager where processes request/hold/release typed, multi-instance resources.
Deadlock detection: build the wait-for graph and detect cycles; report the deadlocked set.
Deadlock avoidance: the Banker’s algorithm safety check on each request.

Prevention strategies (ordered resources / all-or-nothing) with a comparison of trade-offs.

How to solve it
The model. Represent Allocation, Max, Need, and Available matrices plus a request queue. A request is granted only if it keeps the system in a safe state; otherwise the requester blocks. This is the Week 11 coordination material implemented as a working service, not a worked example.

Detection vs avoidance. Detection runs periodically or on block: construct the wait-for graph (project the RAG by resolving assignment/request edges) and DFS for a cycle. Avoidance is proactive: the Banker’s safety algorithm simulates whether all processes can still finish before granting.

Recovery and a real demo. On a detected cycle, pick a victim by a cost function, release its resources, and re-run the safety check. Then tie it to reality: spawn threads that grab pthread mutexes in opposing orders and have the manager observe and report the deadlock the course visualizes in Week 11.

Core syscalls / APIs pthreads (for the live demo), matrix algorithms, graph DFS, pthread_mutex_trylock for observation

Evaluation & acceptance
Graded on the common rubric below. A submission passes when it clears these project-specific acceptance tests, demonstrated live in the Week-12 viva:

A crafted circular-wait scenario is detected and the exact deadlocked set reported.
The Banker’s check grants safe requests and blocks unsafe ones correctly.
Two threads locking in opposing orders are caught by the live demo.
A safe interleaving runs to completion with no false deadlock flagged.
Distinction bar. A working recovery path that breaks a real thread deadlock by victim selection, plus a correct multi-instance detector with no false positives under stress.
